# 爬虫为什么一直 partial，以及爬虫能接过 Muse 的哪些工作

**整理时间：** 2026-11-03 · **代码版本：** `main` `f5d5365`；爬虫修复在 PR #68（`crawl-unblock-event-loop`），未合并
**性质：** 诊断加方案。第 1 部分的原因是本地复现出来的，生产环境日志没看到（原因见 1.5）。第 3 部分是提议，没有实施。

## 1. 爬虫为什么一直是 partial

### 1.1 partial 的意思

`backend/routers/admin.py:73`：一个批次里只要有 **1 行** 报错，整批就记作 `partial`，全部成功才是 `ok`。所以 partial 本身不说明问题有多大，要看报错的是哪几行、是不是一直是同样的几行。

### 1.2 最近 40 次运行（GitHub Actions 日志里每一步的返回 JSON，run 1363–1402）

| 阶段 | 次数 | 处理行数 | 成功 | 报错 | partial 次数 |
|---|---:|---:|---:|---:|---:|
| fetch | 18 | 900 | 864 | 36 | 18 |
| extract | 16 | 1,200 | 1,193 | 7 | 6 |
| tag | 6 | 3,000 | 55 | 0 | 0 |

fetch 每一次都恰好报错 **2 行**（50 行里成功 48 行）。这个规律说明是同样的教会每次都失败，不是随机故障。

### 1.3 从什么时候开始

| 运行 | 时间（UTC） | fetch 结果 |
|---|---|---|
| 1301–1340 | 10/21 – 10/25 22:35 | 每次 50/50，`ok` |
| **1341** | **10/26 04:52** | 49/50，第一次报错 1 行 |
| **1351** | **10/27 14:33** | 48/50，此后每次 2 行 |

10/24–10/28 之间，`backend/`、`requirements.txt`、`Dockerfile`、`render.yaml` 都没有提交，所以原因不在代码改动。10/23 发布 Muse 数据之后，fetch 也连续干净跑了 2 天，所以也不是发布造成的。

### 1.4 为什么同样的教会每次都会被选中

按顺序发生的是：

1. `run_fetch_batch` 遇到某个教会抛出异常，只把 `rows_error` 加 1，**不写任何抓取记录**（`fetch.py`）。
2. `churches_due_for_fetch` 按这个教会主页"最后一次尝试"的时间排序，最久没尝试的排最前（`ORDER BY last_try ASC NULLS FIRST`）。
3. 失败的教会从来没写入新记录，它的"最后尝试"时间一直停在过去，于是**永远排在队首**，每批都被选中，每批都失败。

结果是每批固定浪费 2 个名额，而且 fetch 的"上次完整成功"再也不会更新。现在 `/api/stats` 的 `pipeline_ok` 还是 true，只是因为健康检查看的是"有没有进展"，没看"有没有完整成功"。

### 1.5 复现：robots.txt 里有 NUL 字节

用真实的 `fetch_church` 代码跑了一遍，只替换了数据库：假数据库遇到 NUL 字节就报错，和真实 Postgres 一样（Postgres 的 text 字段不能存 NUL，psycopg 会直接报错）；R2 存储用桩。请求用的是爬虫自己的 user agent，遵守 robots 规则，每个网站一轮。

| 范围 | 网站数 | 异常 |
|---|---:|---:|
| 10/23 发布的网站（新教会和更新的教会） | 1,141 | 0 |
| 目录里的网站（只抓主页，不去重前 8,508 条） | 8,187 | **4** |

4 个异常的原因都一样：`upsert_robots` 想把 robots.txt 的内容存进数据库，内容里有 NUL 字节，于是报错。这一步发生在写主页记录之前，正好符合 1.4 的情况。

| church_id | 网站 | robots.txt 的实际响应 |
|---:|---|---|
| 23227 | oneholyfamily.org | `content-encoding: br`，67 字节，2 个 NUL |
| 47798 | amarillomandir.org | `content-encoding: br`，71 字节，2 个 NUL |
| 98985 | faithvictoryfellowship.com | `content-encoding: br`，70 字节，3 个 NUL |
| 130244 | mtkalutheran.org | 在 `/robots.txt` 返回一个 128 KB 的 HTML 页面，52,561 个 NUL |

- 前三个网站：我们的请求声明只接受 `gzip, deflate`，服务器还是用 Brotli 压缩返回 robots.txt。httpx 0.28 没装 `brotli` 包就不会解压（`requirements.txt` 里只有 `httpx`），于是压缩后的二进制原样存进了 `r.text`。
- 这三个网站的主页都正常返回 gzip，没有问题。出问题的只是 robots.txt。

**没有证实的部分：** 生产环境里每次失败的那 2 个教会是不是就在这 4 个里面。我没有 Render 日志的权限，也没有调用 `/api/admin/crawl/status` 需要的 `CRAWL_TOKEN`。支持这个判断的证据有四条：

1. 失败是确定性的，不是随机的；
2. 失败发生在写主页记录之前；
3. 失败数（2）不超过找到的异常数（4）；
4. 开始时间和这些教会 30 天一次的刷新到期时间吻合。

这些教会之前能抓成功，说明它们的网站在那之后改了返回方式，这一点同样没证实。

要证实的话，看 Render 日志里的 `fetch failed church=`，或者用 token 查 `/api/admin/crawl/status`。另外 2 个可能还没到刷新时间，一旦到期，每批失败数会升到 3 或 4。

### 1.6 修复方案（还没改代码）

1. **robots.txt 内容不对时，按"读不到"处理。**
   - 内容里有 NUL，或者明显是二进制、HTML，就不存进缓存，这个网站当作"robots 读不到"。
   - 保守做法是记一条 `robots-disallow` 的抓取记录，让这个教会进入 48 小时退避。这比把乱码当成"全部允许"更安全，符合 RFC 9309 的要求。
   - 不需要加新依赖。如果要真正读出那三个 Brotli 文件里的规则，需要在 requirements 里加 `brotli`，这是新依赖，要你同意。
2. **单个教会抛异常时也写一条记录。** `run_fetch_batch` 捕获异常后写一条 `fetch_error="exception:<类型>"` 的主页记录，这样任何异常都会进入退避，不会再把队首堵住。
3. **让 partial 能直接看出原因。** 批次返回的 JSON 里附上失败的 `church_id` 和异常类型，以后看 GitHub Actions 日志就能定位，不用再复现。
4. **extract 那 7 行报错**（1,200 行里占 0.6%，6 次 partial）这次没查。它们的模式和 fetch 不同，不是每次固定几行，要另外看。

这些改动都要加测试：一个 robots.txt 有 NUL 的教会，第二次运行时不会再被选中。

## 2. 爬虫和 Muse 工作流的对比（不含 Facebook）

### 2.1 各环节谁在做

| 环节 | Muse（逐行研究） | 爬虫（`backend/scrapers_v2/`） |
|---|---|---|
| **找到新教会** | 网络搜索，扫目录站（churchfinder、oursweb），查宗派名录。共发现 2,394 个目录里没有的教会：网络搜索 1,638，目录站 628，宗派名录 56 | **不做**。只抓数据库里已经有网址的教会 |
| **确认网站是不是这个教会的** | `url_evidence`：网站上的地址或电话和记录一致 | **不做**。网址拿来就用 |
| **读哪些页面** | 主页、活动、新闻、讲道、周报（含 PDF）、到访和联系、儿童页。用真实浏览器，能看到 JS 渲染的内容 | 主页，再加最多 3 个页面（about / beliefs / ministries / services）。只读静态 HTML，不渲染 JS，不读 PDF |
| **怎么读文本** | 人读整个页面 | 先用 trafilatura 抽正文，页眉页脚会被去掉，而地址和聚会时间常常就在页脚。不过原始 HTML 都存在 R2 里 |
| **提取哪些事实** | 是否活跃（12 个月内的日期证据）、地址（以及是不是聚会地点）、电话（个人电话按 D-2 不公开）、聚会时间和语言、儿童项目 | 宗派、神学立场、语言（v3.1 按网页语言推断）、项目列表、风格标签、简介、敬拜风格、引语、信仰告白 |
| **证据** | 每个事实一个 URL 加原文摘录，再经过我们的 `recheck_sources.py` 复核，并绑定事实指纹 | 每个字段带 `_source_snippets`，只检查前 160 个字符是不是原文的子串；引语也做子串检查。没有绑定事实指纹，也不走 recheck 的匹配规则 |
| **新鲜度** | 只在研究时检查一次，过期了要再开复查包 | 每 30 天重新抓一次（每 4 小时 50 个，一天 300 个；9,032 个网站正好一个月一轮）。内容没变就保留原来的提取结果 |
| **规模** | 最近 5 包，5 天交了 433 行；每行预算 8–10 分钟；被 Facebook 限速、批次退回的问题拖慢 | 一天抓 300 个、提取 225 个。可以调大，接口上限是每批 500 个 |
| **覆盖** | 查过目录里的 860 个教会，另有 2,628 个候选（其中 2,543 个有网站） | 生产环境：9,032 个有网站，6,777 个已提取，5,980 个有简介 |

**两边几乎不重叠。** 爬虫回答的是"这个教会是什么样的"（神学、风格、简介）。Muse 回答的是"能不能去、怎么去"（还活跃吗、在哪里、几点聚会、有没有儿童项目）。产品的核心问题是后者，而爬虫目前一点都不做。

另外有一处和项目规则冲突：爬虫 v3.1 会按网页语言推断聚会语言，而 AGENTS.md 要求"不要从名字或族裔推断聚会语言"。网页语言不完全等于名字或族裔，但同样是推断，不是证据。所以这个字段不能直接当作和 Muse 同一类的证据。

### 2.2 Muse 的事实从哪里来（本地 analytics 库，候选粒度，最新检查 10/31）

"来自教会自己的网站"的判断方法：来源 URL 的域名和这个教会的网址相同。

| 事实 | 总数 | 来自自己的网站 | 来自 Facebook | 来自宗派网站 | 其他 |
|---|---:|---:|---:|---:|---:|
| 地址 | 2,261 | **1,802（80%）** | 166 | 139 | 172 |
| 电话 | 1,883 | **1,408（75%）** | 213 | 123 | 158 |
| 聚会时间 | 2,165 | **1,931（89%）** | 38 | 69 | 134 |
| 儿童项目 | 1,130 | **1,025（91%）** | 23 | 6 | 79 |
| 活跃状态 | 2,004 | 1,037（52%） | **731（36%）** | 30 | 228 |

来自自己网站的那部分，又是引用了哪种页面：

| 事实 | 主页 | 第二多的页面 |
|---|---:|---|
| 地址 | **1,221 / 1,802（68%）** | 联系/位置 101，周报/PDF 88，到访 72 |
| 聚会时间 | **1,434 / 1,931（74%）** | 聚会时间页 95，到访 83，周报/PDF 51 |
| 儿童项目 | **480 / 1,025（47%）** | 儿童/家庭页 99，到访 93 |
| 活跃状态 | 426 / 1,037（41%） | 活动 151，周报/PDF 138，讲道 101 |

**结论：** 除了 Facebook，Muse 的大部分事实都是从教会自己网站上读出来的，最多的就是主页。爬虫已经存档了约 9,000 个教会的主页，只是没有去提取这些事实。

## 3. 哪些工作可以交给爬虫（方案）

按价值从高到低排：

### 3.1 新增"到访信息"提取（最有价值）

- **提取对象：** 所有有网站的教会。目录里有 9,032 个，Muse 的候选里有 2,543 个，加起来比 Muse 至今查过的多好几倍。
- **提取字段：**
  - 地址，以及这个地址是不是聚会地点；
  - 聚会时间，包括星期几、几点、聚会类型和语言；
  - 电话，分清是教会电话还是个人电话（D-2）；
  - 儿童项目；
  - 最近一次有日期的活动。
- **读哪些页面：**
  - 用 R2 里存的**原始 HTML**，不用 trafilatura 抽出来的正文，这样页脚里的地址和时间也读得到；
  - 在现有四类页面之外，增加联系/位置/到访、活动/日历、新闻、讲道页面，以及周报 PDF。
- **证据门槛和 Muse 一样：**
  - 每个值都要带 URL 和原文摘录；
  - 用现有的 `recheck_sources.py` 匹配规则和事实指纹去比对**我们存档的那一版页面**；
  - 再走 dbt 现有的显示规则（D-1、D-2、`displayable`）。
- **顺带解决一个老问题：** 按存档的页面核对，就不会出现"首页内容已经换掉、摘录找不到了"的情况（P5）。存档本身记录了抓取时间，证据对应的就是那个时刻的页面。
- **来源要分开标注。** "爬虫提取、摘录已核对"和"Muse 研究、摘录已核对"是两类不同的证据，显示和统计时都要区分。
- **限制：** 摘录匹配只能证明这段文字在页面上，不能证明日期、时间、聚会类型、语言、校区都理解对了。要说"爬虫的准确率达到某个水平"，必须先有一份独立人工判定的样本：
  - 按地区、语言、网站类型分层抽样；
  - 样本里要包括走错校区、活动日期过期、页面上根本没写这件事这几类反例；
  - 不能拿 Muse 的结果当标准答案，Muse 也是一个提取器。

### 3.2 复查和重新引用

WP-0031–0040、0051、0052 这几包复查，和 S 系列"重新引用聚会时间"的任务，本质上都是"再打开页面，确认这段话还在"。这正是爬虫定期重抓加 `recheck_sources.py` 能自动做的事；`repair_excerpts.py` 也已经是我们内部的工具。以后这类工作只需要把 JS 渲染、抓不到的页面留给 Muse。

### 3.3 确认网站是不是这个教会的

把目录或 Muse 给的地址、电话，和网站上写的地址、电话直接比对，结果和 `url_evidence` 一样（`address_matches` / `phone_matches`）。这是确定性的比对，不需要 LLM。

### 3.4 自动扫目录站

churchfinder 和 oursweb 的城市列表可以由程序扫出来，生成线索清单。有网站的线索直接进 3.1。

前提条件：

- 先检查这两个站的 robots.txt 和使用条款。它们之前对 Muse 返回过 403 和 429，**被挡住的不能绕过**。
- 目录站只能用来"找"教会，不能当证据引用（S5）。
- 这是新的数据源，要你批准。

### 3.5 还是要留给 Muse 或人工的

- **给没有网站的教会找网站。** 目录里 93%（约 12.5 万个）没有网站；IRS 名录里 16,880 条加州线索也没有网站。这要靠搜索和判断，搜索 API 是付费的。
- **找不在任何目录里的教会。** 1,638 个靠网络搜索发现的新教会就是这一类。
- **JS 渲染的网站、挡我们爬虫的网站。** 这些 Muse 用浏览器能读，但要守住"不绕过封锁"的规则。
- **难判断的身份问题。** 多个校区、几个会众共用一栋楼、借用别的教会场地、搬了家。
- **需要判断的事实。** 地址是办公室还是聚会地点、几个来源说法冲突。

## 4. 下一步和需要你批准的事

| # | 事项 | 需要批准？ | 说明 |
|---|---|---|---|
| 1 | 修复 partial（1.6 的第 1–3 项）加测试，开 PR | 不需要（如果要加 `brotli` 依赖，需要） | 改动小；合并后要拿实际部署的版本号确认 fetch 恢复成 `ok` |
