## 0. 一句话结论

10/19 立项时的目标，是先把一个城市区做成“访客能放心去”的地图，再往外扩。两周下来，验证流程已经跑通，也真正发布到了生产环境。但现在的产出方式是：Muse 逐行研究，我们逐条复核，还要看 Facebook。这种方式规模扩不上去。Facebook 的频率封锁，加上批次因为格式问题被反复退回，是眼下最直接的两个限速项。11/03 决定暂停 Facebook 验证，先用网站端的能力让项目上线。

## 1. 最初的计划（2026-10-19）

来源：[churchmap_data_quality_dbt_plan.md](../churchmap_data_quality_dbt_plan.md)，以及 10/20 的 [docs/plans/geocode_and_publish_plan.md](plans/geocode_and_publish_plan.md)。

### 1.1 核心问题

> 访客能不能找到一个真实存在的教会，并且放心地去到它现在聚会的地点？

计划明确区分了五件事：HTTP 请求成功、LLM 返回成功、摘要非空、坐标有效、教会位置正确。前四件成立，不代表第五件成立。

### 1.2 立项时的基线（本地快照 `holyhub.db`，2026-05-08）

| 指标 | 数量 | 占比 |
|---|---:|---:|
| 目录记录（OSM 133,929 + 手工 10） | 133,939 | — |
| 有坐标 | 133,929 | ~100% |
| 地址以门牌号开头 | 592 | 0.4% |
| 门牌地址或 Google 地址 | 5,935 | 4.4% |
| 有网站 | 8,508 | 6.4% |
| 试点区（San Bruno–Redwood City） | 77 条 | 其中 6 个有网站，1 个有门牌地址，7 个疑似不属于范围 |

结论：坐标几乎都有，可以导航的地址几乎都没有；目录里混着修道院、寺庙、公司；试点区的覆盖明显不足。

### 1.3 两条线

| 线 | 目标 | 冲突时 |
|---|---|---|
| 产品线 | 先做好一个可信的城市区：San Mateo / Foster City，然后整个 Peninsula | **优先** |
| 案例线 | 一个小而有测试的 dbt 分析层，用来解释产品数字 | 时间不够先砍 |

### 1.4 计划的五步

1. 统计生产环境里可导航地址和坐标的覆盖率。
2. 审核试点区的位置准确性，用同一批记录给 Muse 打分。
3. 通过 Muse 补全试点区缺的信息（URL、Facebook 主页、门牌地址、电话、身份），并找出 OSM 漏掉的教会，包括只有 Facebook 的教会。结果只进隔离区。
4. 记录 LLM token 用量。
5. 搭最小的 dbt 层和一张地图就绪度视图。

### 1.5 关于 Muse 和 Facebook 的原始设定

- 计划里写的是：Muse 是 Meta 自己的浏览 agent，所以 Facebook 主页被列为第二可信的来源，仅次于教会官网；公开群组只能当线索。
- 每个事实都要附原文摘录；原始返回文件不进 git；Facebook URL 不进爬虫队列。

### 1.6 立项时定下的三条规则（§12）

| 编号 | 内容 |
|---|---|
| D-1 | 只显示基督教会众；非基督教场所、修道院、公司隐藏；非三一论的基督教团体（LDS、耶和华见证人等）显示，并用他们自己的名称标注 |
| D-2 | 个人电话（手机、具名个人的线路）永不公开 |
| D-3（FB-1 之后修订） | 只来自教会自己 Facebook 主页的事实可以显示，标注“来自教会 Facebook 主页，检查于某日”。条件：该行为 active、主页 12 个月内发过帖；服务时间要求所引用的帖子本身在 12 个月内 |

### 1.7 完成标准（原文摘要）

- 生产环境的地址和坐标计数能用提交的 SQL 复现。
- 原定人工审核 30 条，实际审了 5 条后停止，由自动复核取代。
- Muse 第 A 批返回、通过校验、打分。
- 新的提取任务记录 LLM 用量。
- 新 clone 下来能复现 dbt build。
- 不声称全国准确率。

## 2. 工作流程实际怎么走

```
OSM 目录快照 (133,939)            ── 自动爬虫 v2（并行，另一条线）──
   │                                 fetch → R2 → extract(LLM) → tag
   ├─ 核实任务：现有教会清单            → 生产库里的网站摘要和标签
   └─ 发现任务：按城市找新教会
        │
        ▼
Google Drive 共享队列  outbox/WP-xxxx/TASK.md        (drive_sync.py publish)
        │  Muse 按 status.csv 取活：先 needs_fix，再 queued，最多同时 2 个
        ▼
Muse 研究：官网 → 活动/新闻/讲道/周报 → Facebook 主页 → 目录站扫一遍
        │  交付 returns/WP-xxxx/ + DONE.md（带哈希）
        ▼
每小时拉取  ChurchMapMusePull (Windows 计划任务 → drive_pull_hourly.sh)
   1. validate_returns.py    机械校验；不过就写 feedback/，状态改 needs_fix
   2. recheck_sources.py     重新打开每个非 Facebook 来源，确认摘录在页面上（绑定事实指纹）
   3. repair_excerpts.py     （按需）事实在页面上、摘录不准时，换成原文
   4. build_seeds.py         合并所有批次 → dbt seeds
   5. geocode_incremental    Census 地理编码（地址绑定的台账）
   6. dbt build              int_location_readiness / int_candidate_readiness → 发布用 mart
        │
        ▼
scripts/publish_verified.py  默认 dry run，出 diff CSV → 业主确认 → --apply（每 50 条一个事务，写 publish_log，可以 --revert）
        │
        ▼
生产环境 Supabase → Render API → Vercel 前端
```

一个事实要能显示，必须同时满足：

1. Muse 给出页面和原文摘录；
2. 我们自己的复核在那个页面上找到这段摘录，并且指纹（值 + URL + 摘录）一致；
3. 通过 D-1、D-2、D-3 规则。

只有 Facebook 来源的事实不经过复核（`skipped_facebook`），走 D-3。

## 5. 遇到的问题

### 数据源本身

**P1. OSM 目录不适合直接上地图。**
- 现象：只有 0.4% 的地址有门牌号；目录里混着修道院、寺庙、公司；试点区 77 条，明显漏了很多教会。
- 处理：D-1 范围规则；Muse 补地址；Census 地理编码。
- 现状：地址缺口只在 Muse 查过的那一小部分里补上了。

**P2. 93% 的教会没有网站。**
- 现象：生产环境只有 6.7% 有网站，所以爬虫再好也只能覆盖这一小部分。
- 现状：没有解决方案。这是全国规模的根本限制。

**P3. IRS BMF 名录只能当线索。**
- 现象：加州有 16,880 条带地址、OSM 和 Muse 都没有的教会线索；Muse 新发现的教会 55% 已经在里面。但教会不报 990 表，倒闭了也不会被撤销登记，所以名录里有很多已经不存在的教会，大约一半的地址像住宅或通讯地址。
- 现状：还没测过“真实且活跃”的比例。测量脚本不在 repo 里。

### Muse 的研究质量

**P4. 只看首页。**
- 现象：WP-0001–0010 的 624 条里有 433 条是 unresolved，几乎都是“首页上没有日期”，Facebook 从来没打开过。
- 处理：brief v3.3 要求深度搜索，`check_deep_search` 强制执行。

**P5. 摘录我们复核不了。**
- 现象：WP-0031–0033 的 213 条 active 中，111 条没通过复核。其中 43 条是我们自己的复核程序被 403；其余是 JSON-LD 时间戳、首页轮换的内容、YouTube 链接。
- 处理：brief v3.5，校验脚本拒收这几类。

**P6. 反复引用已经被 robots 挡住的页面。**
- 现象：WP-0039 的 22 条失败里，有 17 条重复引用了上次失败的 URL。
- 处理：#58 拒收重复引用被 robots 挡住的页面。“同一 URL 一律报错”这条没加，因为它会误伤 8 条后来验证通过的行。

**P7. 把质量规则当成少做的理由。**
- 现象：WP-0042 用“深度优先”当理由，每个城市大约只报 1 个，而目录站上大约有 250 条。
- 处理：brief v3.6，`check_unresearched`（#59、#60）。

**P8. 批次因为格式问题卡住（当前最大的吞吐问题）。**
- 现象：WP-0044–0048 全部 needs_fix。主要原因是 run log 里 D12 目录扫描那一行的格式不对（缺 `unresearched U`，或者写成了表格），另外有一些目录条目没研究完。
- 影响：433 行已经交付但没入库（之前误数成 472）；10/30 起只有 80 行入库。
- 11/03 处理：这 5 包登记在 `muse_handoff/sweep_accepted.csv`，内部验收入库。以后的包：目录扫描的记录怎么写都行，只有 Muse 自己写明“还有 U 条没研究、且没到上限”时才退回；没写 U 的，算出差额写进状态备注，由我们来看。
- Muse 那边：WP-0044 从 10/30 退回到现在，11/02 发了提醒，还没修好。
- 需要决定：退回的理由里，“格式不对”和“内容没做完”应该分开对待。格式问题可以考虑由我们这边宽松解析或自动修正，不必整批退回。

### Facebook

**P9. Facebook 限速，没法扩大规模。**
- 现象：10/26 11:27 PT 第一次出现 "You're Temporarily Blocked / going too fast"，Facebook 第 2 轮做到第 20 行就停了，41 分钟后还在封锁。WP-0012 到 WP-0052 共 27 个批次的 run log 提到封锁或限速。11/03 上午又被封了。
- 价值：Facebook 确实有用。第 1 轮把 37 条 unresolved 里的 32 条翻成了 active；WP-0039 的 44 条验证里有 28 条靠 Facebook。现在 map_ready 的 891 条里，384 条的活跃证据来自 Facebook。
- 限制：Facebook 只能用一个授权账号、慢速浏览，被封期间就整个停下。速度上不去，账号本身也有风险。
- 决定（11/03）：暂停 Facebook 验证，见第 6 节。

### 我们自己的复核和基础设施

**P10. 复核程序有盲区。**
- 被 403 或 robots 挡住的页面、JS 渲染的页面、字母间加了空格的 PDF，都会让本来正确的事实显示为“没找到”。
- `--resource-blocked` 修复能挽回一部分，但不是全部。

**P11. 每小时拉取依赖个人电脑。**
- Windows 计划任务、WSL、G: 盘挂载，三样都要在。
- WSL 一重启，`/mnt/g` 就会消失。10/25 计划任务不见了，要业主手动重新注册（`register_pull_task.ps1`）。
- 周末关机（正常，不算故障）。
- 当前检出的分支就是线上在跑的代码，切到 PR 分支会让拉取任务跑旧代码（10/22 发生过）。
- 有并发锁冲突（10/22、10/30 出现过 "previous pull still running"）。

**P12. 爬虫运行时会拖慢搜索。**
- 现象：trafilatura 解析和 boto3 读写 R2 是同步调用，阻塞了事件循环。
- 处理：当前分支有修复（把它们放进 `asyncio.to_thread`），**还没提交、没跑测试**。
- 另外：近 7 天 31 次 partial，fetch 自 10/25 起没有一次完整成功。原因还没查。

**P13. 产出受业主时间限制。**
- 发布需要业主提供生产环境的 `DATABASE_URL`，并确认 diff。
- 重新注册计划任务、挂载 G: 盘也需要业主操作。

### 规模

**P14. 按现在的打法跑不完全国。**
- 开头那段估算：全国约 37 万个教会，按每天 55–100 行要 10–18 年；就算每天 2 包、每包 80 行的上限也要 6 年多。这些数字出自那段估算本身，我没有逐项复现。
- 方向上可以确定：瓶颈是“一个 agent 一行一行深查，我们一条一条复核”这种方式本身。去掉 Facebook 能减少被封、每行省点时间，但改变不了数量级。

### 还没解决的决定（计划 §12 遗留）

- Muse 产出能不能公开再利用（条款待定）。
- Google 地址/电话等补充字段在分析层里能不能直接用（条款待查）。
- dbt 没接 CI，因为快照是本地文件。
- `mart_coverage_snapshot` 的 `as_of_date` 还停在 2026-10-19。D-3 的“12 个月新鲜度”是按 build 时的 `as_of_date` 算的，正式发布前要确认传入的是当天日期。
